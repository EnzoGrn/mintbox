# 0009. Framework-free domain model

- **Status:** Accepted
- **Date:** 2026-11-03

## Context

The domain model is the heart of Mintbox: the aggregates, their rules and their events
(see the [domain model](../domain/)). I want it to be readable and testable on its own,
without a database, a Spring context or a mocking framework.

The usual shortcut in Spring applications is to put JPA annotations directly on the domain
classes. It saves code, but persistence then shapes the model: JPA needs a no-argument
constructor and mutable fields, lazy loading creates proxies that break `equals`, and it's
easy to end up with setters and a model that mirrors the tables.

## Decision

- **Each module is split into packages with clear roles:**

  | Package | Contains | May depend on |
  |---------|----------|---------------|
  | `<module>` | The module's public API: query interfaces, views, domain events | `shared`, other modules' public APIs |
  | `<module>.domain` | Aggregates, value objects, business rules, repository interfaces | `shared`, its own module's events, the JDK |
  | `<module>.application` | Use cases that load aggregates, call them and save them | `domain` |
  | `<module>.infrastructure` | JPA entities, external API clients, web controllers | everything above, and the frameworks |

- **The domain and `shared` packages use plain Java only.** An ArchUnit test fails the
  build if they depend on Spring, JPA, Hibernate or Jackson.
- **The domain declares the repository interfaces it needs** (ports), and the
  infrastructure implements them with JPA (adapters).
- **Persistence uses separate JPA entities**, mapped to and from the domain objects in the
  infrastructure package.
- **Aggregates record their domain events** in memory. The application service publishes
  them through Spring once the aggregate is saved, in the same transaction, so that
  Spring Modulith's event publication registry stores them.
- **Identifiers are generated by the domain** as time-ordered UUIDs (version 7), so an
  aggregate has its identity before it is saved.

## Consequences

- Domain tests are fast plain unit tests: no Spring context, no database, no mocks.
- The model is free to express the business: immutable value objects, no setters, no
  no-argument constructors.
- Every aggregate needs a JPA entity and a mapping. For simple aggregates like the catalog
  entry, this looks like duplication. I accept it for consistency, since the same pattern
  pays off on aggregates with real rules, like listings and orders.
- Loading an aggregate always loads it entirely, which matches the aggregate rules
  anyway (load the whole aggregate, change it, save it).

## Alternatives considered

- **JPA annotations on the domain classes:** less code, and the most common approach. But
  the persistence constraints listed above leak into the model, which is what I want this
  project to avoid.
- **jMolecules with its bytecode plugin:** keeps the domain annotation-light and generates
  the JPA plumbing at build time. Elegant, but the generated code is invisible when reading
  the project, which works against a portfolio meant to be read.
- **Spring Data JDBC:** maps aggregates more directly than JPA, with fewer surprises. It
  would still require annotations or naming conventions in the domain, and JPA is what the
  rest of the stack (Flyway, Testcontainers examples, Hibernate tooling) is built around.
